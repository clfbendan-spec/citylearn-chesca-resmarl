# §1 温度项 `band`

**当前值**：`band = 1.0`、`lower_exponent = 2.0`、`higher_exponent = 3.0`

⚠️ 2026-09-28：band 2.0 的尝试**已证伪并回退到 1.0**（保留此记录，勿重蹈）

曾经的动机（f4328081 实测，band=1.0 + floor 0.05 + span 0.40）：

- 92.8% 的制冷电量花在"KPI 舒适区"(|T−SP|<2) 内：B1 86.2% / B2 97.3% / B3 96.5%；
- 与「同场景无控制基线」比（BaselineAgent = 热泵不控、按理想负荷交付，等效开度
  0.19~0.21；用 online_evaluation_1/2208 步重建）：B1 31.0%→14.4%/成本 0.886、
  B3 5.4%→4.1%/0.956（双赢），但 **B2 3.4%→4.2%、成本 1.260（+26%）**，
  District 成本 1.034 > 1.0 ⇒ 比"什么都不做"还贵；
- 推理：奖励免罚区只有 [SP, SP+1]（1°C 宽），而 KPI 舒适区是 [SP−2, SP+2]
  ⇒ 以为"放宽到 ±2 就能省下为 ±1 买的那部分电"。

判决实验 532d4cdc（**只改 band=2.0**，跑满 320 轮，同 seed 同数据）：

```
    B2 低温**全程 23~35%**（对照 band=1.0 的 f4328081：3.0%）；
    District 成本 1.034 → **1.129**；B2 成本 1.260 → **1.436** ⇒ **明显有害**。
```

为什么失败（根因 —— 别再只改 band）：奖励里有三个量都**跟着 band 一起变**：

- ① 冷侧立方罚起点 = SP − band：−1.0 → **−2.0**
  ⇒ dT=−1.5 的罚从 (−1.5)³=−3.375 变成 (−1.5)（②线性项）=−1.5，**弱 2.25 倍**；
- ② 浅冷线性罚区间：[SP−1, SP) → [SP−2, SP)；
- **带内免罚窗下界 = SP − band×cold_near_free_frac**：SP−0.5 → **SP−1.0**
  ⇒ dT∈[−1,0) 这段制冷**完全不罚**（原本是要罚的）。
- ⇒ band 一翻倍 = 冷侧约束整体松一档 ⇒ 策略在 [−2,−1] 区间继续吹 ⇒ B2 过冷爆炸。
- ⇒ 结论：**冷侧的立方罚是当前唯一压住 B2 过冷的力量，不能再松。**

同批但独立的变量：电费项 cost_weight=50（见 §4）在 band=2.0 的烂底子上仍把
District 成本从 1.129 拉回 1.019、B2 低温 24.2%→12.7% ⇒ **该项有效，予以保留**。

若将来仍想"放宽热侧"：必须做**非对称**实现（新增 hot_band，只作用于 ③④ 分支与
hot_act 触发点；冷侧 ①② 与免罚窗继续用 band=1.0），不要动 band 本身。

# §2 过热「动作保底」（治"高温不制冷"）

**当前值**：`hot_act_floor=0.15`、`hot_a_per_c=0.026`、`hot_a_cap=1.0`、
`hot_act_weight=110.0`、`hot_act_penalty_cap=130.0`、`hot_act_min_over_c=0.25`、
`hot_a_need_mode='load'`、`hot_over_weight=15.0`、`hot_over_tol=0.005`、
`hot_over_tol_frac=0.15`、`hot_over_penalty_cap=60.0`

**口径**
`a_need = min(hot_a_cap, hot_act_floor + hot_a_per_c × 超出带温差)`（`'const'` 口径）
或 `max(a_ref, 上式)`（`'load'` 口径，现行）
罚 `R_act_hot = −hot_act_weight × max(0, a_need − act_cool)`，封顶 `hot_act_penalty_cap`

## P1（已废弃，勿重蹈）

曾把目标收到 0.25~0.35 → ab24d164 实测 B1 高温 29.0%→77.9%。
教训：把要求调低只是让「缺口」这个数字变好看，策略反而更不开冷
（B1 act 均值 0.127→0.073、act<0.05 占比 23%→52%）。缺口的正确用法是
「抬高要求 + 加大权重逼策略去补」，而不是降低要求让缺口消失。

## Step 2（2026-09-29）：`hot_a_need_mode` —— a_need 从"手挑常数"改为**物理量导出**

旧口径：a_need = hot_act_floor + hot_a_per_c × over（= 0.15 + 0.026·over）——
这是个**一刀切常数**，与当前负荷无关 ⇒ 低负荷时刻要求过度开冷、高负荷时刻要求不足。
实测后果（f4328081 / d0f8b032）：B2 平均开度 0.27 却 dT=−0.80（比无控制还冷），
72~80% 的制冷电量是"白吹"，81.9% 花在 dT≤0 的"已经够凉"时段。

新口径（'load'）：a_need = cooling_demand ÷ 本步热容量，
热容量 = 额定电功率 × 当前 COP —— 由环境逐时算好注入奖励
（注入见 _stash_actions_for_reward 的 Step 2 段；奖励侧见 custom_comfort_reward.py）。

- 物理含义：把室温拉回设定点所需的最小开度；
- **没有手挑常数、也没有任何按楼写死的值** —— 负荷与热容量都从环境读，
  因此对每栋、每个时刻自动不同。这正是"该开多少由物理决定，而不是由我们规定"；
- COP 随室外温度在 3.1~10.2 间变化（实测），所以热容量必须逐时算，不能用额定值。

判据：B2 的 applied 均值应靠近负荷需求（≈0.12~0.20，现在 0.27）；dT p50 由 −0.80
升到 ≈0；"白吹"电量占比应明显下降；日志里「其中负荷导出=」应接近 100%。
回退：改成 'const'（旧的常数式口径，代码保留）。

# §6 电池套利 `bat_weight`

**当前值**：`bat_weight = 50.0`（P-11 试 100 已证伪 ⇒ 回退）

P3′（2026-09-29）：电池套利项权重（唯一旋钮；0 = 关闭）

为什么加：储能此前是**零信号维度** —— r_bat 恒 0、cost_weight=0、温度项看不到电池
⇒ SAC 在 2 个对回报无影响的维度上自由游走。0e6894aa 实测：B2 电池吞吐 **760 kWh**
（同场景无控制基线 = 0）、毛电耗 +12.7% 但净电耗只 +2.8% ⇒ 差额是往返损耗；
B2 成本因此 +15.6%（1.156），District 0.986。

⚠️ P-1 修订（2026-09-29）：项的口径由「绝对电价」改为「**价差**」

```
     旧：r_bat = −w × price × (充电 − 有效放电)      ← 充电恒为负 ⇒ 大 w 下"永不充"最优
     新：r_bat = −w × (price − p_ref) × (充电 − 有效放电)，p_ref = 价格滑动均值
```

依据（140a32d7 逐栋电池盈亏，_diag_bat_arb.py）：

- B2 贵的核心是**择时反了**（16~18 时充电，高峰充占比 20.9%、价差 −0.0069 ← 反向套利）；
- B3 证明策略**能**学会套利（高峰窗放电 29.6%、价差 +0.0097）；
- 但旧式在 w=50 下把充电整体压死 ⇒ B3 的高峰放也从 29.6% 掉到 6.6% ✗ ⇒ 套利长不出来。

新式（**带 max(0,·)**）：平价充/放 = 0（中性，可自由充）、高峰放 = 大奖、
高峰充 = 重罚 ⇒ 只奖励"真正落在高价窗"的放电 ⇒ 学习信号从"少罚"变成"窗口内有奖" ✓
⚠️ 不取 max(0,·) 会**倒贴平价充电**（−w×负×chg>0）：_p1p2_smoke40 实测 B1 充 406kWh
而零套利（价差 −0.0000）却项值为正 +309.6 ⇒ 过度循环（ramping 1.214、毛电耗 1.088）✗

为什么现在才可能做对：唯一的旧尝试 d0f8b032 用「净用电」计费 ⇒ 把制冷与储能**混罚**
⇒ 策略把制冷预算从 B1 搬到 B2（District 成本 1.034→1.093、B2 不适 4.2%→12.8%）⇒ 证伪。
本项**只含电池自身**：r_bat = −w × price × (充电 kWh − 有效放电 kWh) ⇒ 与制冷解耦。

场景依据（本次实测）：电价只有两档 —— 平价 0.0302（91% 时间）/ 高价 0.0661（16~18 时，
每天 3h），峰谷比 2.19×；电池 3.32 kW / 4.00 kWh / η0.95（B3 1.61 kW / 3.30 kWh）
⇒ 单日套利上限 ≈0.124 元；B2 日账单 ≈0.70 元 ⇒ 理论空间 ≈18%。
标定：单步量级 = 4kWh×0.03 ≈ 0.12，温度项 1~5 ⇒ 取值 30~50。

# §8 入口脚本与生成器约定（横幅 / 文档字符串里的说明）

**当前状态**：`Multi-agent-train.py` / `Multi-agent-eval.py` 都是 `_gen_marl_split.py`
从 `Multi-agent.py` 生成的 ✓ —— 它们的"横幅 + 模块文档字符串"由生成器模板注入，
其余部分（工具层 + 自己的流程/参数表）与源文件逐字一致 ✓

## 为什么要有这两个入口（而不是只用一体化脚本）

一体化脚本一次运行必须把 SAC 从头训完（数小时），训练结束立刻跑评估 ✗ ——
想「训一次、反复评估」或「换参数反复评估」都得重训，代价极高 ✗。
拆成两个入口后：**训练脚本只训练并存 checkpoint，评估脚本只加载 checkpoint 跑仿真** ✓

## 为什么保留"用不到"的名字（有意为之，不是漏删）

两个入口里都存在**对方才用得到**的函数与常量：eval 里留着 `run_mid_eval` /
`MINI_EVAL_*` / `MID_*` / `TRAIN_BATCH_SIZE` / `DEFAULT_TRAIN_SCHEMA`，
train 里留着 `print_kpis_for_java` / `build_decision_recorder` / `record_step_trace` /
`decision_trace_path` / `run_nocontrol_cost_ref`。

保留理由：**未调用的函数定义与模块常量在 import 时不产生开销**，而逐个删除会让生成物
与源文件的结构差异越来越大 —— 每多一处差异，就多一个"源文件改动后生成器失效"的标记 ✗。
保留它们，才能保证「改 `Multi-agent.py` → 重跑生成器」**永远一步成功** ✓
代价是这两个文件里会有未被调用的名字，属**有意为之**。

## 生成器的切分边界（改源文件时不要动坏这些标记）

| 区段 | 范围 | 三个入口是否都有 |
|---|---|---|
| 【共享区】启动逻辑 | `if __name__` 起 → `train_schema = ...` 之前 | ✓ 三方逐字相同 |
| 【训练准备段】 | `train_schema = ...` → `probe = _AGENT_ENV_CLS(train_env_config)` | 仅 train / 一体化（eval 换成评估准备段）|
| 【训练流程段】 | `probe = ...` → `log_console('训练完成，开始测试仿真...')` | 仅 train / 一体化（eval 换成加载 checkpoint；train 执行到此存档退出）|
| 【评估段】 | `env = _AGENT_ENV_CLS(eval_env_config)` → 文件末尾 | ✓ 三方逐字相同 |
| 参数表 | `parse_args()` 内各参数块 | 各自裁剪（train 无 `--no-trace`；eval 无训练参数；`--trace-every` 已于 2026-10-05 全局移除 ⇒ 见 §17）|
| 横幅 / 文档字符串 | 文件头 | 由模板注入（`BANNER_*` / `*_DOC_BODY`）|

⚠️ 生成器靠**精确的字符串标记**定位（`MARK_*`），动到标记会导致生成失败（会**报错停止**，
不会静默出错 ✓）。

## 评估期早停为何被整块移除（2026-10-01）

原先有 `EARLY_STOP_*` 常量 + `--no-early-stop / --early-stop-pct / --early-stop-after`，

# §9 奖励实现内部（`custom_comfort_reward.py`）的记录

## 9.1 ⚠️ 构造函数形参默认值 ≠ 项目实际配置（**动手前必读**）

`CustomComfortReward.__init__` 的形参保留了**历史默认值**：

```
hot_act_floor=0.30  hot_a_per_c=0.11  hot_a_cap=0.60
hot_over_weight=30.0  hot_over_tol=0.03  hot_over_tol_frac=0.0
cool_cost_weight=0.0  cold_near_weight=45.0  bat_weight=50.0  bat_loss_weight=0.0
```

而**项目实际生效的值在 `Multi-agent.py` 的 `CUSTOM_REWARD_KWARGS`**：

```
hot_act_floor=0.15  hot_a_per_c=0.026  hot_a_cap=1.0
hot_over_weight=15.0  hot_over_tol=0.005  hot_over_tol_frac=0.15
cool_cost_weight=2.0  cold_near_weight=45.0  bat_weight=50.0  bat_loss_weight=0.0
```

**原因**：CityLearn 在构造环境时总是用
`reward_function_kwargs=CUSTOM_REWARD_KWARGS` 实例化本类 ⇒ 形参默认值**从不参与**
训练/评估，它只是"最后写在那里的那一版" ✗（`band` 则相反：`CUSTOM_REWARD_KWARGS`
里显式给了 1.0 ✓）。

**由此确立两条纪律**：

1. **改奖励参数 → 只改 `CUSTOM_REWARD_KWARGS`** ✓；`custom_comfort_reward.py` 的形参默认值
   属于签名占位，不要拿它当配置（改了也不生效 ✗，反而误导读者）；
2. **任何"显式构造本类"的代码都必须传完整参数** —— 传空 dict 或省略参数会**静默**使用
   上面那套历史默认值 ⇒ 实验结论失真 ✗。`check_reward_equivalence(reward_kwargs, ...)`
   因此把 `reward_kwargs` 设为**必填**（省略直接 `TypeError`，宁可直接失败也不要静默测错 ✓）。

## 9.2 mid-eval 的「高温/低温%」为什么改由奖励类自己累计（P1′）

**问题（三次运行实测，2026-09-25）**：

1. `run_mini_eval` 原先用 `_read_building_series` 去读「楼栋对象」上的温度/设定点，
   在自定义窗口（head/tail 探针）下读到的值与策略真实轨迹不一致：
   - `623a9e8d` r430：mid-eval 报 B1 低温 19.8%，决策推演/导出 KPI 只有 1.2%（**差 18 倍**）
   - `b30240d4` r300：mid-eval 报 B3 合计 22.5%，真 KPI 只有 5.9%（**差 3.8 倍**）
2. 同代码同 seed 的两次运行（`b30240d4`/`de83deaf`，仅 `TRAIN_EPOCHS` 不同）前 100 轮
   B1/B2 的 mid-eval 逐点完全相同（⇒ 权重相同），但 B3 从第 20 轮就分叉
   （52.4% vs 80.7%）—— 即「同一个权重下 B3 的读数会变」，读数**不可重复**。
   B3 全季温度跨度仅 1.6°C（B1 7.2 / B2 3.8），是这个 bug 的放大镜。
3. 而 mid-eval 的「高温/低温%」正是 **best-ckpt 选择 + 三个早停判据的唯一输入**
   ⇒ **读数错 = 判据全错**：已导致 `de83deaf` 按错误读数选了第 310 轮，真 KPI 差 34pp，
   且「超标面积」与真 KPI 之间**连单调关系都没有**
   （0.495→0.171 / 0.345→0.217 / 0.310→0.112）。

**为什么改用本类累加**：`calculate()` 是被 CityLearn 在 `step` 内部调用的，拿到的
`observations` 就是策略本步**真正使用的那一份**（决策推演里 `[奖励计算] T=` 与
`[观测动作] T=` 逐位相同）⇒ 这里的读数必然与决策推演/导出 KPI 同源 ✓。
绕开楼栋对象的取值路径后，窗口/绝对相对下标错位这一类问题不再可能影响判据 ✓

**口径与导出 KPI 完全一致**：只统计 `occupant_count > 0` 的步；高温 = `T > 冷设定点 + band`；
低温 = `T < 热设定点 − band`（band 取 `comfort_band`）；`mean_T` 统计所有楼步（含无人步），
与原实现语义保持一致。
**回退方法**：把 `run_mini_eval` 里 kpi 的主读数换回 `legacy_*`（影子值一直在同步计算）。

# §10 best-ckpt 选择指标（`BEST_CKPT_*` / `P4_COST_HINGE`）

> 这一段的核心教训是：**选择器选错轮次，比策略学不好更致命** —— 后面几百轮的进步会被整体丢弃。

## 10.1 为什么需要 best-checkpoint（P2-D）

动机（`da94e80a` 实测）：训练期 best「最差和」= 0.421（第 190 轮）→ 末次 0.628（**退步 49%**），
末次 mid-eval B1 合计 63.8% vs 历史最优 36.6%。训练后期策略漂移 ⇒ "末次权重"比"历史最优权重"
差得多，而评估阶段一直用末次权重 ⇒ **白白丢掉已经训出的好模型**。
做法：每次中期评估若创新低 → 把当前 SAC 状态另存到 `BEST_CKPT_DIR_NAME`；训练结束后若该目录
可用 → 用 best 权重替换 model 再做正式评估。与 `CKPT_DIR` 完全独立：best 快照不会被"定期保存"
覆盖，续训时也能跨进程沿用 ✓

## 10.2 选择指标 = 「超标面积」（P5-A）

```
指标 = Σ max(0, 各栋「高温+低温」合计 − BEST_CKPT_TARGET_SUM)
       + BEST_CKPT_TIEBREAK × Σ(各栋合计)
```

- 首项直接对齐业务目标"每栋 ≤15%"：超标越少越好（全部达标时为 0）；
- 次项是**总不适**，权重见 `BEST_CKPT_TIEBREAK`（旧版给的 1e-6 权重已证伪）。

**为什么不用「最差和」（P2-D 原始判据）**：`max(hot)` 与 `max(cold)` 可能来自不同楼 ——
`16a3fa48` 实测 B3 从 9.6%→4.9% 会把 `max(cold)` 拉低 ⇒ 判据降到 0.418（第 260 轮），
而同轮 B1 已 41.7%、B1 真正最优在第 140 轮（35.9%）⇒ **选错权重**。

**为什么也不用「max(逐栋合计)」**：它只压最差的栋，会牺牲其他栋。同一份曲线实测：

| 判据 | 落点轮次 | B1 | B2 | 超标面积 |
|---|---|---|---|---|
| `max(逐栋合计)` | 第 150 轮 | 34.3% | 33.4% | 37.7% |
| **超标面积** | **第 140 轮** | 35.9% | 28.7% | **34.6%** ← 更优 |

六种候选判据在同一曲线上的超标面积对比见 `_smoke_test_p5a2.py`。

## 10.3 修「全部达标后指标失去分辨力」（P1，2026-09-28，`b972fb6c`）

**现象**：目标线是硬阈值，三栋一旦全部 <15%，超标面积恒为 0 ⇒ 指标退化成"第一个达标的轮次"，
此后更好的权重再也进不来。旧 tie-break 是 `1e-6·max(合计)`，差值仅 2e-8，先被
`MID_MIN_GAIN=0.01` 的接受门槛挡死：

| 轮 | B1 / B2 / B3 | 超标面积 | Σ合计 | 旧指标 |
|---|---|---|---|---|
| 90 | 14.2% / 7.8% / 3.2% | 0.000 | 0.252 | 1.42e-7 ← **被选中**（正式评估用它）|
| 140 | 10.7% / 10.1% / 2.4% | 0.000 | 0.232 | 1.07e-7 ← 实际更优，却被门槛挡住 |

⇒ District 0.084（第 90 轮）vs 约 0.077（第 140 轮）。

**做法**：① 次项换成 `BEST_CKPT_TIEBREAK×Σ合计` —— 全部达标时指标 = `0.05×Σ合计`，
直接按"总不适"排序；② 接受门槛与 `MID_MIN_GAIN` **解耦**（`BEST_CKPT_MIN_GAIN`）——
这是**必须一起改**的：`0.05×ΔΣ` 在 ΔΣ=2pp 时才 0.001，沿用 0.01 门槛则次项永远无效（就是上面的 bug）。

**为什么不是"只把 1e-6 调大"**：0.01 门槛是按首项量级定的，要把次项放大到越过它，就会在
"仍有超标"时反客为主（超标面积 0.35 vs Σ合计≈1.0，量级差 3 倍）。两项分开取值才稳：
**主序由首项定，次项只在"首项相同"时起作用**。

## 10.4 成本项的三轮判决：P-4（加入）→ P-4d（移除）→ P-13（hinge）

**P-4 加入的动机**（`1a21ef2c` / `140a32d7` 实测）：指标只含"不适" ⇒ 训练越久，策略只被舒适度
推着走，**成本无人看守就一路漂走**：

| 轮数 | B2 成本 |
|---|---|
| 20 轮 | 0.994 ✓ |
| 40 轮 | 0.987~0.992 ✓ |
| 160 轮 | 1.023（账单计价）/ 1.068（择时计价）✗ |

而且 best-ckpt 也随之落在"舒服但更贵"的快照上（`140a32d7` 落在 R70、`1a21ef2c` 落在 R140）⇒
用户核心诉求"B2 成本 < 1"被这个盲区拖住。做法：`metric += P4_COST_WEIGHT × 成本率`，其中
**成本率 = 本次 mid-eval 的 Σprice×max(0,net) ÷ 同场景「无控制基线」的同量**；
无控制基线 = 在同一条探针上以**恒定冷却动作 a=0.5** 跑一遍（当前 P-1 映射下 `a=0.5 ⇒ applied = a_ref`
= 恒等跟随 = 按数据集理想负荷交付），储能维给 0 ⇒ 口径与奖励的 `cost_raw` **完全同源** ✓

**P-4d 判决：移除（λ=0）**。判决数据（`808692fb` 逐轮探针，探针读数与正式评估**逐楼逐位一致**已证）：

| 轮 | B1 / B2 / B3 合计 | Σ合计 | 成本率 | 备注 |
|---|---|---|---|---|
| R20 | 3.3 / **9.0** / 6.1 | 18.4% | **0.9012** | ← λ=0.10 时被选中（最便宜的探针）|
| R90 | 2.8 / **5.4** / 5.1 | **13.4%** | 0.9351 | ← 真正的更优解 |

机理：λ=0.10 时「成本项变化 0.10×0.0339=0.0034」> 「舒适项变化 0.05×0.0499=0.0025」
⇒ 成本把舒适压过去 ⇒ **选择器为 3.4% 的成本白扔了 B2 3.6pp 的舒适**（9.0% → 本可 5.4%），
并且两次运行（160/320 轮）的 best-ckpt 都停在 R20 ⇒ 后面 300 轮的舒适学习全被丢弃 ✗。
**结论：选择指标只按舒适排序**（成本由奖励侧的效率项负责，不由选择器代管）；P-4 的成本统计 /
参照 / 逐轮成本率**全部保留**，只作诊断输出。若要恢复线性成本项：置 0.05（等权）或 0.10（成本优先），
但需同时接受上述副作用。

**P-13 加入 hinge**。动机（`8328e690` 逐轮，160 轮）：成本随训练**单调上漂**
（0.9050(R10) → 0.9582(R160) ✗），而舒适持续改善（Σ合计 0.1213 → 0.0978 ✓）⇒ best-ckpt 按纯舒适选
⇒ 落在"舒服但更贵"的 R50 ✗，最终 B2 = 1.072（B2 净电只 +0.5% ✓，但**隐含均价 +7.0%** ✗
⇒ 病灶是时段 ✗）。

与 P-4d 的区别（为什么这不是"线性成本项"的死法）：P-4d 移除的是 `λ×ratio` 的**线性**项
（它把 R20 这种"最便宜但最不舒适"的轮次选出来 ✗）；hinge 只在 ratio 超过目标线时才给分
⇒ **达标轮之间仍完全按舒适排序** ✓，只有当"成本明显漂走"时才把选择拉回合规轮 ✓ ——
正好服务"B2 降到 1 以下"这个目标 ✓

```python
term += P4_COST_HINGE['w'] × max(0, Σ_b cost_b / Σ_b ref_b − P4_COST_HINGE['target'])
```

**已定标（2026-09-30 冒烟 A/B/C 三档对照）：w=0.3、target=0.90 设为默认** ✓

- **为什么是 0.90 而不是 0.93**：实测**单栋 ≈ 1.07~1.09 × district 成本率** ⇒ 0.93 只能保证
  district ≤0.93（B2 实测仍 1.016 ✗）；0.90 ⇒ **B2 实测 0.981 ✓**
- **为什么 w=0.3**：`0.3×0.05 ≈ 0.015` ≈ 舒适次项（`0.05×Σ合计`≈0.005）的 3 倍 ⇒ 足以把选择拉回
  合规轮，但达标轮之间不干扰（冒烟 C 里 District 不适 3.1% 与纯舒适版 3.0% 持平 ✓ 无代价）
- 回退：`P4_COST_HINGE['w'] = 0.0`（立刻回到"只按舒适"）；配套 CLI：`--p4-hinge-w` / `--p4-hinge-target`
- **P-12（`cost_weight`）已判决出局** ✗：w=10 时 B2 反而 1.049 ✗，且实测把电池套利掐死
  （B2 电池净现金流 +4.96 → −0.03，均放价 0.0523 → 0.0343 ✗）⇒ 保持 `cost_weight=0` ✓

**⚠️ 实现上的坑（已踩过）**：hinge 必须用**可变容器**（dict）承载，不能用模块级标量 ——
`--p4-hinge-w` 的覆盖发生在 `main()` 里，而 `main` 在此之前已引用过该名字 ⇒ 直接 `global` 赋值会触发
`SyntaxError: name ... is assigned to before global declaration`。
**注意 `ast.parse` 查不出这类错误，必须用 `python -m py_compile` 校验** ✓

## 10.5 `BEST_CKPT_METRIC_VER`：口径版本与拒绝继承

`BEST_CKPT_METRIC_VER = 3`。续训时若断点里的版本 ≠ 本值 ⇒ **拒绝继承**：
旧口径在全达标时是 ~1e-7、新口径是 ~1e-2，量级不可比；硬继承会让新快照永远刷不进去

⇒ 与前一版的数值都不可比（常数偏移虽不影响同轮比较，但跨版本继承会让"是否创新低"的判断失效）。

`BEST_CKPT_MIN_GAIN = 0.0` 的依据：测评是"贪心 + 固定 seed + 整段"的**确定性过程**，
指标差 = 策略的真实差异（不是采样噪声）；取 0 的代价仅是快照保存次数变多
（≤ 每 `MINI_EVAL_EVERY` 轮 1 次）✓

# §11 P-1 动作映射（`COOL_LOAD_*` / `COOL_REMAP_*` / `COOL_SPAN_*`）

> 这一节解决的是"**动作怎么解释**"：策略输出的 a∈[0,1] 映射成实际的制冷开度。
> 映射错了，再好的奖励也拉不动（见 §11.5 的"白吹"事故）。

## 11.1 把中立点从"固定开度"改为"逐时负荷跟随"（P-1，2026-09-29）

动机（`e6cf8272` 逐栋取证 + 同场景 NOCONTROL 对照，脚本 `_diag_b2_cost.py`）：
三栋的负荷需求几乎相同（`a_ref`：p50 0.16 / 0.16 / 0.17，p90 0.43 / 0.44 / 0.47，
max 0.82~0.90；超过旧映射上沿 0.43 的步占比 9.7% / 10.5% / 13.0%），但**相对负荷的偏离完全不同**：

| 楼 | 负荷等效开度 | RL 实际开度 | 偏离 | 结果 |
|---|---|---|---|---|
| B1 | 0.2060 | 0.1676 | −18.6% | 成本 0.874、不适 3.5%（双赢 ✓）|
| B2 | 0.1879 | 0.2487 | **+32.4%** | 成本 1.163、不适 7.4%（**被无控制支配** ✗）|
| B3 | 0.2110 | 0.1924 | −8.8% | 成本 0.936、不适 0.7%（双赢 ✓）|

**根因**：旧映射 `applied = floor + (1−floor)×span×a` 的**中立点固定**（a=0.5 ⇒ 开度 0.24），
比负荷所需的 0.19 **高 25%**。B1/B3 的策略把输出均值学到 0.305 / 0.371（会"少吹"），
而 **B2 的输出均值停在 0.499 ≈ 初始化值 0.5**（学出了"随 dT 单调"的形状，但整体水平留在初始化点）
⇒ 系统性超吹：63.5% 的步超吹、平均超额 0.1145 开度、多花 780 kWh（= B2 总电量的 63.6%），
把室温压到 `dT≈−1.2℃`（旧奖励"带内免罚窗 [SP−1, SP)" 的冷边）⇒ 越过 KPI 冷线即低温不适 5.9%。

> ⚠️ **关键认识**：B2 的奖励罚分已是三栋最高（累计 −21041，B1 的 2.3 倍），其中冷罚 −3.72/步
> ≫ 超吹罚 −1.64/步 ⇒ **不是"奖励没罚"，而是策略没走到那个点** ⇒ **加权重治不了**，
> 必须改映射结构 ✓（这条认识直接解释了"为什么调奖励权重对 B2 无效"）

**新做法**：把中立点钉在**本步的负荷所需开度 `a_ref`** 上，用**乘法**（相对负荷的倍率）：

```
applied = a_ref × ( MIN_FRAC + (MAX_FRAC − MIN_FRAC) × a )
```

- `a = 0.5`（策略初始化点）⇒ 倍率恰为 1.00 ⇒ `applied = a_ref` = 无控制基线的"**恒等跟随**"
  （实测比值 0.993）⇒ 三栋都从"不浪费"出发；**B2 的初始化即（近）最优 ⇒ 病根被结构性消除** ✓
- `a > 0.5` ⇒ 相对负荷多吹（前馈预冷/顶热，上限 `MAX_FRAC`）；`a < 0.5` ⇒ 少吹
  （下限 `MIN_FRAC = 0.75` ⇒ **最多少吹 25%，不可能塌到 0**）
- 天花板/地板都变成"负荷相对"⇒ 不再有"高负荷步顶格吹不动"，也不会有"低负荷步白吹一大截"
  （旧映射在 `a_ref=0.03` 的步也会给到 0.16）
- 工作点在 `a≈0.5` = tanh 梯度最大处（∂a/∂z=0.5）⇒ 不必再靠 floor 托举

## 11.2 为什么必须是**乘法**（第一版加法式已证伪）

`applied = a_ref + span×(a−0.5)`（第一版）在 `a<0.5` 时 applied 会**塌到 0**
（`a_ref=0.19`、`span=0.6` 时 `a≤0.18` 就归零），而奖励的超吹罚是**单边**的（只在 `a>0.5` 侧
持续往下推）⇒ 策略一旦滑进 tanh 低斜率区就**爬不回来**：
冒烟 `_p1_load_smoke`（20 轮）实测 B1 的 `a_raw` p50=0.072（30.4% 的步贴 0）、
`applied` 均值 0.045 vs 需求 0.185、`dT=+5.21` ⇒ **高温 93% 的"关冷自锁"** ✗。
改乘法后 `a=0` 也仍有 `0.75×a_ref` 的制冷 ⇒ 物理后果有界、热罚梯度能把它拉回来 ✓

## 11.3 带宽取 ±25%（第一版 ±50% 已压缩）

实测有效区间是 `mult(B1)=0.77`、`mult(B2)=1.05`、`mult(B3)=1.00`（逐步对齐统计
`_check_p1_aligned.py`），±25% 正好覆盖。
⚠️ 第一版取 ±50% 时 B1 的策略漂到 `mult=0.667`（欠吹 33%）⇒ 由于**相对形式的缺口随负荷成比例
放大**，高负荷步被伤得最重 ⇒ B1 高温 11%（冒烟 `_p1_load_smoke40`）⇒ 收紧到 ±25%，
最坏情况只有 −25%，且 `a=0.5` 仍精确对应 `mult=1.0` ✓

## 11.4 P-2：上沿 1.25 → 1.10 已证伪并回退（2026-09-30）

判决实验 `1a21ef2c`（160 轮，与 `140a32d7` 同时改了电池项 ⇒ 温度差异归因于本项）：

## 11.5 P-6′(i)：区分「`a_ref` 合法为 0」与「`a_ref` 取不到」（2026-09-30）

**事故**（`7c7ae2b2` 正式评估 trace 逐组分解，脚本 `_q_b2cold.py` + `_q_fallback.py`）：
B2 低温步 99 步里 **91 步（91.9%）**的实际动作 = **`0.05 + 0.38×a`**（逐位吻合）——
那是**回退映射**的公式，不是 P-1 的 `a_ref` 倍率式（后者比值实测 0.95、误差 <1e-3）。
原因：`_use_load = _aref > 0.0` 把"本步理想负荷恰好为 0（**合法**：不需要制冷）"和
"取不到（异常/越界）"混为一谈 ⇒ 前者也走了回退 ⇒ **无负荷步上白吹 0.226 开度**，
室温被压到 `dT≈−3.5`（KPI 低温线 −2 之外）⇒ **B2 低温 6.2%、成本 1.045 的共同来源**。
**做法**：`a_ref` 合法（含 0）⇒ 一律走 P-1 倍率式；其中 **`a_ref=0` 时给一个极小的自由量**
（`COOL_LOAD_NOLOAD_MAX×a`，`a=0.5 ⇒ 0.04`），既消除"无负荷白吹"，又保留"必要时补救"的能力
（不给 0 是防止在 `a_ref=0` 的步上彻底失去制冷手段）；**取不到** ⇒ 才回退旧映射。
全楼同一常量、同一公式，无按楼参数 ✓

## 11.6 Step 1：动作重标定的「去 per-building 化」（2026-09-29）

**原则（用户提出）：学习本身不应该有针对单栋建筑的规则。** 手写的 `{楼号: 值}` 表等于把
"哪栋该吹多少"的人类先验硬编码进环境 —— 策略无从学到它、也无法迁移到别的楼；而且一旦某栋
表现不好，只会诱使我们去改表（C′-4 `{1:0.14}`、floor `{1:0.05}`、span `{1:0.40}` 三次干预
都是这么来的，其中前两次已被实测证伪 ✗）。
**做法**：两张按楼查表 ⇒ 两个**全局标量**，三栋一视同仁：

```
applied = COOL_REMAP_FLOOR + (1 − COOL_REMAP_FLOOR) × COOL_REMAP_SPAN × a
```

当前 `floor=0.05`、`span=0.40` ⇒ `applied = 0.05 + 0.38·a ∈ [0.05, 0.43]`（B1/B2/B3 完全相同）。

**为什么这仍属"标定"而非"规则"**：

- 动作的物理含义是"额定功率的百分比"，而三栋的有用开度区间都落在 `[0, ~0.45]`
  （实测：B1 中立 0.15、B2 理想负荷等效 0.12~0.19、B3≈0.20；探针：`eff=0.30` 已 `dT=−4.46°C`）
  ⇒ "把有用区间铺满 `a∈[0,1]`"是**对动作语义的一次性归一化**，与楼栋无关 ✓
- 附带把 tanh 分辨率统一提升约 2.5 倍（B2/B3 原先 `applied=a`，在 `[0,1]` 上有 3 倍冗余）
- floor 的唯一作用是防止策略漂到 `a→0` 的 tanh 饱和区自锁（历史实测：`floor=0` + 纯缩放会让
  B1 在 R10 就锁死 98% 高温），它对三栋同样生效 ✓

**楼栋差异从哪来：从观测学。** P6-A 已把「负载率 `cooling_demand/nominal_power`」
「能力比值 `nominal_power/max(nominal)`」「楼栋 identity one-hot」放进观测 ⇒
策略有足够信息区分三栋，不需要（也不应该）由我们喂表 ✓

> 另注：`COOL_SPAN_ENABLE` / `COOL_REMAP_SPAN` 的历史（"只给 B1" 的 P2 方案、Step 1 已撤销该做法、
> SPAN 取值必须让"奖励要求"落在策略可达范围）见代码常量处的注释 —— 那一小片**保留在代码里**
> （它是当前口径的一部分），未搬入本文档。

# §12 训练规模与采样口径（`TRAIN_EPOCHS` / `TRAIN_BATCH_SIZE` / `fragment` / `MIN_SAMPLE_TIMESTEPS_PER_ITERATION`）

> 这一节是"训练量"的三次翻车与两次定标。**结论先给**：`TRAIN_EPOCHS=320`、`TRAIN_BATCH_SIZE=512`、
> `ROLLOUT_FRAGMENT_LENGTH="auto"`、`MIN_SAMPLE_TIMESTEPS_PER_ITERATION=100` —— **这四个数别动**。

## 12.1 训练量曾经是硬瓶颈（P4-1 / P8-2）

- 原设置 `TRAIN_EPOCHS=30` × SAC 默认 `train_batch_size=256`：三栋均分后每栋只有几千 agent-step，
  连完整 episode 都跑不了几次 ⇒ 个别 policy 动作饱和（B1 `act∈[0,0.004]`、B3 从不低于 0.098，
  **对奖励不响应**）。
- P4-1：小评估实测 120 轮时策略仍在明显改善（过热触发 31.7%→3.7%、平均回报 −45→−24、末两轮还在降）
  ⇒ 是"**没收敛**"而不是"奖励设计错"。
- P8-2：曾砍到 60/100 轮，结果 P8-1 的新奖励曲线（`a_need` 调高 75%、`cold_near` 调高 50%）让策略
  需要更长学习时间（100 轮时 B1 `act=0.07~0.11` vs `a_need=0.39~0.50`，缺口反而比 P7 更大；
  B2 相关系数从 +0.474 退到 +0.182）⇒ **训练量是硬瓶颈，不是权重调得不够重**。
- 360 轮 ≈ 2.8 h（按 28s/轮）；投票制大概率在 200~280 轮触发，仍留 100+ 轮余量 ⇒ 现取 320。

## 12.2 `train_batch_size` 只影响 learner（P9-1 已废大 batch）

**每轮采样量 = `rollout_fragment_length` × worker 数，与 `train_batch_size` 无关**；
`train_batch_size` 只决定 learner 每轮从回放缓冲区**取多少条训练**。
P9-1 实测：`batch=4096` ⇒ 每轮学习 131s → **560s（慢 4.3 倍）**，且 SAC 在大 batch 下收敛困难
（`c64d3146` 第 60~100 轮 B1 高温卡在 90.5%，而 P7 同等轮次 50.0%）⇒ **大 batch 方向已废** ✗

## 12.3 ⚠️ `fragment` 不能乱动（P15-1 / P16-1 / P17-1 三次翻车）

起因：`d533266f` 日志里「学习样本 = +513000 / 5 轮」被当成**单轮**的真实梯度量，推出"重放比 68:1"
的伪结论 —— 那个数其实是真数（100 批 × 1024 × 5 轮 = 512,000 ✓），是**读数单位搞错**。

| run | fragment | 每轮采样 | 每轮训练(agent) | 结局 |
|---|---|---|---|---|
| `c3f346df` | auto(=100) | 100 | ~102,600（≈100 批）| 可用：KPI 平均不适 0.334 ✓ |
| `d533266f` | auto(=100) | 100 | ~102,600 | P13-1，窗口平台 33~35% |
| `a7499f77` | 1000 | 1000 | **258（1 批）** | 崩 0.934 ✗ |
| `0f73a200` | 500 | 500 | **1,026（1 批）** | 崩 0.939 ✗ |

⇒ 每轮采样量提到 500/1000 后，**训练量塌到 1 批/轮，策略必崩**（退化成"从不制冷"）；
而 100 env-step/轮 时训练量会自动放大到 ~100 批/轮 ⇒ **`fragment` 必须保持 `"auto"`**。

## 12.4 「每轮采样固定 100」的根因（RLlib 源码）

`SACConfig` 把 `min_sample_timesteps_per_iteration` 覆盖成 **100**（`sac.py:129`；基类默认 0），
而 `Algorithm.train()` 会**反复调用 `training_step()` 直到本轮累计采样 ≥ 该值**（`algorithm.py:3610-3622`）。
每次 `training_step()` = 1 次采样调用（采 `fragment×envs_per_worker×max(workers,1)` 个 env-step）
+ 权重指定的若干次训练调用（每次 1 批 `train_batch_size`）。

⇒ **每轮训练批数 = ceil(100 / (fragment × max(workers,1)))** —— 与"数据量"是**同一枚硬币的两面**：
改 `fragment`/`workers` 只是把训练量除来除去 ✗，**真正的数据量旋钮一直是
`min_sample_timesteps_per_iteration`** ✓

## 12.5 `TRAIN_INTENSITY` / `native_ratio` 的口径（C′-2）

```
native_ratio = train_batch_size / (fragment × envs_per_worker × max(workers+1, 1))
s = training_intensity / native_ratio
权重 = [round(1/s), 1] (s<1) 或 [1, round(s)] (s≥1)
```

权重 `[a,b]` = 每个 round-robin 循环里「a 次采样调用 : b 次训练调用」。
实测基线（`3c03ad11`，workers=0，fragment=1）：100 env-step 采样 / ~100 批 × 1024 训练
⇒ `trained/sampled ≈ 1024`，与 `native_ratio = 1024/(1×1×1) = 1024` 吻合（自检脚本 `_diag_train_amount.py`）。

当前取值 `MIN_SAMPLE_TIMESTEPS_PER_ITERATION = 100` ⇒ `training_intensity = train_batch_size`
⇒ 权重 `[1,1]`：

- 与历史基线**逐位等价** ✓
- 开并行后自动变成「采样 ×(workers+1)、**训练量不变**」✓（若改成 `train_batch_size` 的倍数，
  则 `workers=4` 时权重变 `[1,5]`，训练量随 worker 数同步放大 5 倍 —— 只在"严格维持 UTD"的
  对照实验里才这么设）
- ⚠️ `min_sample` 与 `intensity` 是**一件事**，必须一起改（否则启动日志的「配比自检」会告警）
- C′-3 试过把采样目标提到 1000（"数据 ×10"）⇒ **已实测证伪** ✗（代价单轮 ×5、收益不成立）

## 12.6 「训练量塌陷」告警线

`TRAIN_BATCHES_PER_ROUND_MIN = 20`：进度行里每轮训练批数低于此值即判"训练量塌陷" ——
P15-1 / P16-1 两次翻车正是这个形态（模型退化成"从不制冷"、KPI 不适 0.93+）✓

## 12.7 `REPLAY_BUFFER_CAPACITY` / `CKPT_STORE_REPLAY_BUFFER`（续训继承经验池）

**问题**：SAC 的 RLlib checkpoint 默认只含「网络权重 + optimizer + 采样/训练计数器」，
**不含 replay buffer**。续训后采样计数器已恢复（远大于 warmup 阈值）⇒ SAC 跳过 warmup
立即学习，但经验池是空的 ⇒ 只能从"当轮采的 100 env-step"里采样（`train_batch_size=512`）
⇒ Q 函数的学习目标分布从"180 轮历史经验"突变为"只有当前策略的新样本" ⇒ 价值估计偏移、
策略剧烈重新适应 ✗

**实测（`a78b6d05`）**：源任务第 180 轮 B1 合计 38.5%（hot 32.7 / cold 5.8），续训后第 200 轮
翻转为 65.9%（hot 1.8 / cold 64.1）—— **10 轮内行为定性反转**，最差和 0.626 → 0.752。

**做法**：打开 RLlib 官方开关 `store_buffer_in_checkpoints`（`algorithm.py:2918` 保存 /
`2967` 恢复；`MultiAgentReplayBuffer.get_state/set_state` 在
`multi_agent_replay_buffer.py:358/371` 已实现），并用 `REPLAY_BUFFER_CAPACITY` 限制体积 ——
SAC 默认 `capacity=1e6`，长训后会膨胀到 GB 级 ✗

**取值**：容量按 env-step 计（`MultiAgentBatch.count = env_steps`）；本数据集每轮 100 env-step，
360 轮 = 36000 < 50000 ⇒ 不触发 eviction，能保留全部经验 ✓

**代价**：checkpoint 从约 8 MB（仅权重）膨胀到约 80 MB（权重 + 经验池 ~70 MB）；
`model.save()` / `SAC.from_checkpoint()` 各多约 1~2 秒；`CKPT_EVERY=20` 是覆盖式保存，
磁盘占用不累积（固定目录）；best 快照（§10.1）同样是 ~80 MB。

**注意**：历史断点**都没有**经验池 ⇒ 打开开关后第一次续训仍是空池（恢复时 RLlib 会打
warning，入口脚本也会在 `[续训]` 行明确提示）。要彻底生效需先跑一次"含 buffer"的完整训练。

# §13 中期评估（mid-eval）判据与"探针 vs 真实 KPI"的一致性

> 早停、投票止损、单栋恶化保护、best-ckpt 选择**全部**建立在中评读数上 ⇒ **读数错 = 判据全错**。
> 本节记录"读数怎么错的、怎么修好的"。

## 13.1 判据不能用奖励值

奖励是**引导信号**（含 `−110×缺口` 这类人为大项），它变大不代表不适比例变小 ✗。
判据必须与导出 KPI **完全同口径**：只统计「有人」步（`occupant_count > 0`）；band 取楼栋
`comfort_band`（本数据集 2.0）；高温不适 = `T > 冷设定点 + band`、低温不适 = `T < 热设定点 − band`。

## 13.2 窗口：head → head+tail → **full**（两次读数事故）

| 方案 | 问题 | 实测证据 |
|---|---|---|
| `head`（前 288 步）| **低估** | "过热触发 3.7%" vs 全季 KPI 高温 19.4%（**差 5 倍**）✗ |
| `head`+`tail`（最凉 12 天 + 最热 12 天）| **系统性高估** | 极端天气占 100% 而全季只占 26%；`035d3f80`：mid-eval 三栋合计 85.5% vs 同轮全口径 52.0%（**差 33.5pp**；B3 偏差 +20.3pp）✗ |
| **`full`（整段、start=0）** | 代价 574 → 2207 步（≈13s → ≈52s/次）| 与正式评估**完全同源** ⇒ 中期曲线与真 KPI 趋势一致 ✓ |

⚠️ 更关键的一层：**`tail` 的初始条件本身就是错的** —— `start≠0` 时楼栋用 CSV 静态室温 +
全新 LSTM 隐状态起步，不是"跑到第 1920 步时的真实状态"（见 `build_probe_env` 的 ⚠️ 说明）。

后果链：mid-eval 的超标面积与真 KPI **连单调关系都没有**
（0.495→0.171 / 0.345→0.217 / 0.310→0.112）⇒ 而早停/投票/恶化判据全建立在它上面 ⇒ **判据会反向**。
实证 `af7823a3`：早停因「B1 恶化到 50.2%」触发，而**同期全口径在改善**（0.115→0.077）✗

## 13.3 五个早停判据（触发原因都会打到控制台）

| 判据 | 常量 | 说明 |
|---|---|---|
| ① 达标即停 | `MID_STOP_WHEN_GOOD` | 所有楼 高温 ≤ `MID_TARGET_HOT` 且 低温 ≤ `MID_TARGET_COLD`。**P1-B 起遵守 `min_train_epochs`**：原先不受限 ⇒ `b033d51b` 第 20 轮就停，而那次"达标"是假阳性（正式评估 B1 高温 86%）✗ |
| ② 投票制停滞止损（推荐）| `MID_STOP_BY_VOTE` | 逐栋比较"高温+低温"合计是否优于上次；优于上次的楼数 ≥ `ceil(MID_VOTE_RATIO×楼数)` 记为"仍在进步"，连续 `MID_VOTE_PATIENCE` 次达不到 ⇒ 判停滞 |
| ②' 旧的「最差和」| `MID_STOP_BY_SCORE`（默认关）| 保留备查 |
| ③ 单栋恶化保护 | `MID_STOP_ON_WORSEN` | 某栋连续 `MID_WORSEN_PATIENCE` 次高于「自身最优 + `MID_WORSEN_MARGIN`」⇒ 停并点名 |
| ④ 稳定收敛即停 | `MID_STOP_WHEN_CONVERGED` | **全部楼**连续 `MID_CONVERGE_PATIENCE` 次低于 `MID_CONVERGE_SUM`（默认 7%）才停 |
| ⑤ 崩坏止损 | `MID_STOP_ON_CRASH` | 见 §13.5（只体检一次，不受最小轮数限制）|

**五者都只是"跳出训练循环" ⇒ 仍照常跑正式评估并导出 KPI**（Java 拿得到结果）✓

**为什么不能一次定生死（② 为何要 `MID_VOTE_PATIENCE`）**：中期评估自身有噪声
（同参数两次跑 B1 高温 20.0% vs 34.4%）；单窗口"2 栋没变好"经常只是抖动 ——
`da6627c7` 与 `2685a524` **都在第 40 轮出现过抖动**，之后继续变好。设 1 会让这类跑被误杀 ⇒ 默认 3 次（≈60 轮）。

**为什么需要 ③（多数票的盲区）**：`f4693695`：B1 从 33.2%（140 轮）一路恶化到 55.7%（300 轮），
而同期 B2/B3 在改善 ⇒ 每 20 轮都判"优于上次 2/3 栋" ⇒ **一路训到最大轮数，白烧 27 分钟且导出更差的模型** ✗

**为什么需要"全部楼都收敛"（④ 的由来）**：训练进程是**全局共享**的（同一 learner / 回放缓冲区 /
`train()` 循环）⇒ 为一栋收敛停训会直接切断其他栋。`75a95510`：B3 从第 300 轮起稳定 <7%（连续 6 次），
但若当时停训，**B1 会停在 29.7%、B2 停在 38.4%** ✗。阈值 7% 的由来：高低温都非负 ⇒ 合计<7% 蕴含
两个方向都<7%，比验收线（各<10%）更保守；"连续 3 次"是因为中期评估噪声大。

## 13.4 为什么从「最差和」改成「逐栋投票」

旧判据 = `max(高温) + max(低温)`，被**单栋最差值**主导。`2685a524`：第 20→180 轮 B1 高温
91.7%→16.1%（大幅改善），但 B2 低温一直在 25~30% ⇒ 「最差和」只从 1.187 降到 0.463，
**判据几乎失效**（"改好一栋"根本反映不出来）✗。改成逐栋投票后，B1 变好就能被看见
（`2685a524` 全程 2~3 栋优于上次，从未误停）✓

## 13.5 判据⑤ 崩坏止损的判据表（P17-1）

为什么不用「最差和」阈值：可用模型早期的最差和同样在 1.2~1.3（`c3f346df` 第 30~80 轮 1.28~1.31）
⇒ 用分数阈值会把好跑误杀 —— 这正是 `MIN_TRAIN_EPOCHS` 存在的理由。
用什么判据：**单侧饱和**，在第 100 轮体检一次（`CRASH_GUARD_EPOCH`）：

| run | 第 100 轮 max高温 / max低温 | 最终结局 |
|---|---|---|
| `c3f346df` | 0.740 / 0.399 | 可用（整段平均不适 0.334）|
| `d533266f` | 0.622 / 0.384 | 可用候选（窗口平台 33~35%）|
| `a7499f77` | **0.000 / 0.947**（B1 全程过冷饱和）| 崩（0.934，act≈0.019）|
| `0f73a200` | **0.000 / 0.938**（B1 全程过冷饱和）| 崩（0.939，act≈0.017）|

⇒ 第 100 轮「某栋低温 > 80%」（`CRASH_GUARD_MAX_COLD`）就足以判死；高温侧阈值 90%
（`CRASH_GUARD_MAX_HOT`）覆盖"从不制冷"那一端 ✓

## 13.6 训练轮数区间

- **最小轮数 `MIN_TRAIN_EPOCHS = 160`**：在此之前一律继续训练（判据②/②'/③ 不生效；判据① 仍可生效）。
  依据：实测 B1 高温到第 180 轮仍在单调改善（91.7%→16.1%），第 20~60 轮几乎看不出方向（都在 88~92%）
  ⇒ 早期下"停滞"结论必然误判（`e4d0c6cf` 曾在第 80 轮被误判停掉 ✗）
- **最大轮数 `MAX_TRAIN_EPOCHS = 320`**：硬上限，到了无条件停；Java 传入的 `--train-epochs`
  视为该上限（向后兼容）；若 min>max 会自动收敛到 min=max ✓

## 13.7 P1′ 两套读数自检

`MID_KPI_SRC_TOL = 0.02`（2 个百分点）：中期评估同时算**奖励侧**与**旧楼栋对象**两套读数，
差异超阈值就打 `[自检-警告]`；**判据一律采用奖励侧**（原因见 §9.2）✓

# §14 观测维度与动作映射的结构性尝试（`OBS_*` / `COOL_FLOOR_*` / `COOL_SPAN_*`）

> 这一节回答两个问题：**给策略看了什么**（观测维度）与**动作怎么解释**（映射）。
> 结论：观测可以加"条件信息"，但**不能加先验**；动作映射**不能做硬干预**（下界会冻结控制权）。

## 14.1 观测里加的三维（P6-A / Step2B）

| 维度 | 常量 | 内容 | 为什么加 |
|---|---|---|---|
| ① 能力比值 | `OBS_CONTEXT_CAPACITY` | 绝对热负荷 vs 绝对制冷能力（绝对值比值）| 负荷那一维由原有 `cooling_demand` 提供，**二者在策略内部相乘**即可 |
| ② 楼栋身份 one-hot | `OBS_CONTEXT_IDENTITY` | n_b 维 | 提供"我是谁"这个事实，兜底保证可分 |
| ③ 本步 `a_ref` | `OBS_CONTEXT_A_REF` | 「理想负荷所需开度」（逐时、物理量导出）| 见下 |

**③ 为什么必须给**（Step2B）：此前观测里**唯一的负荷信号 `cooling_demand` 实测是"设备刚交付了多少"**
（自证），它只能靠 `T−SP` 反推 ⇒ **必然滞后 + 过冲**（实测 B2 多吹 37%、65% 的步过量）。
而 NOCONTROL 的动作**就是** `a_ref` 本身（比值 0.993、相关 0.995）⇒ 把这一维给策略，
它只需学一个**近似恒等映射**，而不必从温度二阶反推 ✓

**两条设计约束**：

- ①②③ 都只是**条件信息**，不含任何"该多开还是少开"的先验 —— "怎么用"仍完全由学习决定
  （奖励与网络结构均未改动）；
- 为什么加在 `RLlibMultiAgentEnv` 这一层（而不是 CityLearn 的 wrappers）：CityLearn 层是
  `central_agent=True` 的"**所有楼拼接**"向量，只有 RLlib 层才按 agent 拆分（3 agent × 35 维）
  ⇒ 在 CityLearn 层追加**无法被正确拆分** ✗；
- 为什么常量特征不归一化也有效：它扮演 meta-RL 里的"任务上下文"，策略可以拿它做条件；
  若走 `NormalizedObservationWrapper`，常量会被压成 0（min=max）而失效
  ⇒ 本层在**归一化之后**拼接、自己控制量级 ✓

> **红线（吸取 P9-1′ 教训）：新增维度必须落在 `[0,1]` 且"不放大温度类信息"** ✓

## 14.2 C′-4 冷却下界：已证伪并回退（2026-09-28）

背景：早期观察到 B1 把制冷开度压在 `[0.002, 0.010]`（p50=0.004），同时室温比设定点高 +7.6°C、
KPI 过热 98.2% ⇒ 当时判断为"关冷自锁"，于是给冷却维加**实测中立开度**作为下界
（`applied = floor + (1−floor)×a_policy`，floor≈0.14）。**两条独立证据证明这个判断是错的**：

**【证据 1｜零和】** B1 的实际开度（由 `cooling_electricity_consumption/nominal_power` 反推；
trace 里的 `act_cool` 是策略原始输出，有下界时不可用）与 KPI：

| run | C′-4 | eff p10 | eff p50 | eff p90 | cv | B1 热 | B1 冷 | B1 合计 |
|---|---|---|---|---|---|---|---|---|
| `057f3849` | 无 | 0.039 | 0.1217 | 0.2141 | 55.0% | 20.2% | 1.8% | 22.0% |
| `88809afe` | 有 | 0.141 | 0.1436 | 0.1460 | 9.4% | 17.8% | 12.4% | 30.2% |
| `94062fa4` | 有 | 0.148 | 0.1655 | 0.2287 | 23.0% | 2.4% | 19.0% | 21.4% |

⇒ 下界把 eff 的**下沿**从 0.039 抬到 0.148（**关不掉冷**）⇒ 冷 +17pp / 热 −18pp，
**合计几乎不动**：它只是把"热超标"**平移**成"冷超标"，**没有增加任何控制精度**，
同时把该维控制权**冻死**（cv 55%→9.4%）✗

**【证据 2｜策略远胜任何常数】** 全季"固定开度"离线探针（`_probe_floor_fullseason.py`，
7 档 × 2207 步，显式用基类环境绕开下界）给出"不学习"的上限：

| 楼 | 最优常数 | 该常数下的不适 | 策略实际 | 策略胜出 |
|---|---|---|---|---|
| B1 | 0.15 | 30.4% | 21.6% | **+8.8pp** |
| B2 | 0.15 | 30.3% | 22.6% | **+7.7pp** |
| B3 | 0.20 | 19.7% | 2.4% | **+17.3pp** |

⇒ **任何"固定值 / 下界 / 重标定"类干预都不如策略自己** ✓。同探针给出全季中立开度
B1≈0.150 / B2≈0.167 / B3≈0.182，且同一开度在"凉季段→热季段"**漂移 1.2~2.1°C**
⇒ **单一常数必然在全季某段是错的**。

## 14.3 三条教训

1. **别拿"欠训练快照"当"结构性自锁"** —— 立论依据 `8b1a6954` 只跑了 60 轮
   （其 B1 `dT p50 = +8.80°C` 是**没学会**，而 320 轮时 B1 自己就把开度爬到了 0.12）；
2. **映射侧硬干预会冻结控制权** —— 而日志只报"已设置"，**不会报警"策略已放弃该维"** ✗
   （这类失败是静默的，必须靠 `eff` 的分布/cv 才看得出来）；
3. **trace 的动作列必须落"建筑实际执行"值**，否则整套诊断走偏。

## 14.4 "课程式下界"也已证伪（`e722911a`）

P1（2026-09-28）曾改成"随轮数线性衰减的下界"（早期治死锁、后期还自由度）：
`floor(epoch) = COOL_REMAP_FLOOR × max(0, 1 − epoch/COOL_FLOOR_UNTIL)`。结果：

| floor | 0.127 | 0.096 | 0.049 | 0.002 | 0.000 |
|---|---|---|---|---|---|
| B1 高温 | 30.9% | 52.7% | 86.9% | 97.9% | 97.9% |

⇒ B1 的高温与 floor **完全同步**：**下界一撤就打回死锁**，且与"完全无引导"的 `480c1f47`
的 97.9% 一模一样。**机理**：下界的本质是**外部托举**，它绕过了"策略自己走不动"这件事，
所以必须一直开着；而一直开着又让"减小 a 的边际收益"变小 ⇒ 策略懒得调 ⇒ 冻结（cv 55%→9.4%）。
**「托举 ↔ 冻结」二选一 —— 这是死结** ⇒ 故当前 `COOL_FLOOR_UNTIL = 0`（不衰减）✓

## 14.5 为什么最终用"缩放"（SPAN）而不是下界

**根因（两个数字钉死）**：C′-4 的映射把**中立开度 0.15 放在 `a=0`**，而 `a=0` 处 tanh 深度饱和
（`∂a/∂z = 0.5(1−tanh²) ≈ 0.005`）⇒ 热侧 `∂R/∂act = +110` 传到 actor 只剩 ~0.5
—— **策略"想动也动不了"** ✗

**做法**：线性缩放 `applied = SPAN × a`，把中立开度 0.15 挪到 **`a = 0.5`（tanh 梯度最大处）**：

- 有效梯度 `0.86×0.005 = 0.004` → `0.40×0.5 = 0.20`（**放大约 50 倍**）；
- 策略初始化 `a≈0.5` ⇒ `applied = 0.20` ⇒ **一开始就站在舒适点**；
- 跑到 `a=0` ⇒ `applied=0` ⇒ 立即过热 ⇒ 热罚梯度 `+110×0.40 = +44` **能把它拉回**
  （而旧 floor 方案下贴 `a=0` 时 applied 仍是 0.14、不会过热 ⇒ **没有纠偏力**）；
- 值域 `[0, 0.40]` 够用：探针实测 `eff=0.30 → dT=−4.46°C`（已严重过冷）、`0.40 → −7.01`。

## 14.6 SPAN 的取值约束（改 SPAN 必读）

- 必须让"奖励要求"落在策略**可达**的动作范围内 —— 热侧要求 `a_need ∈ [0.15, 0.30]`
  ⇒ 取 `SPAN=0.40` ⇒ 工作区 `a∈[0.375, 0.75]`，既可达、又避开 tanh 两端饱和；
- 中立开度 0.15 ⇒ `a=0.375`（该点 `∂a/∂z ≈ 0.44`，属良好梯度区）；
- ⚠️ **改 SPAN 时必须逐 over 档验算 `a_need/SPAN ≤ 1`** —— 旧值 `SPAN=0.30` 配旧
  `a_need(0.30+0.11·over)` 时最低一档也要 `a=1.09` ⇒ **全程不可达**（"恒欠吹"的典型成因）✗
- 回退：`COOL_SPAN_ENABLE=False`（回到 `applied=a`）

# §15 评估的奖励口径：训练时保存、评估时读回（`reward_config.json`）

**问题**：奖励权重（`bat_weight` / `bat_loss_weight` / `cost_weight`）既决定训练"学什么"，
又出现在评估产物里（决策推演 `decision_trace.json` 的 `reward_kwargs` 与逐项 reward）。
早期评估入口允许现场传这三个开关 ⇒ 推演里的 reward 数字可能**不是策略被训练时用的那个目标** ✗
—— 而这些数字正是用来解释"策略在优化什么"的 ⇒ **口径必须唯一** ✓。

**做法**（2026-10-05）：

- **训练侧写**：每次保存 checkpoint（定期 `CKPT_EVERY` / best 快照 / 训练收尾）都在该 checkpoint
  目录写一份 `reward_config.json` = `{saved_at, saved_by, reward_kwargs}`，其中 `reward_kwargs`
  是**本次实际生效**的 `CUSTOM_REWARD_KWARGS`（含训练时的命令行覆盖 ✓，不是文件默认值 ✗）。
- **评估侧读**：准备段（**必须排在 `build_env_config` 之前** ✗ —— 该 dict 是在建环境时被拷进
  `env_kwargs['reward_function_kwargs']` 的 ⇒ 建完再改会静默失效）按
  `<checkpoint>/reward_config.json` → `<checkpoint>/*/reward_config.json`（兼容"传父目录"）
  的顺序查找，找到就 `CUSTOM_REWARD_KWARGS.update(...)` ✓。
- **评估入口裁剪**：`--bat-weight` / `--bat-loss` / `--cost-weight` 三个开关**已从评估入口删除** ✗
  （生成器 `_gen_marl_split.py` 用**纯 ASCII 行做区间锚点**裁剪 —— 这些参数的 help 里有全角引号，
  逐字复制极易出错 ✗）；源文件 `Multi-agent.py` 与 `Multi-agent-train.py` 保留这三个开关 ✓。
- **回退**：找不到 sidecar（**历史断点** ✗）⇒ 用当前代码默认 + 一行 warning（同 §12.7 处理 ✓）。

**实测（同一 checkpoint、同一数据集）**：

| 跑法 | `exported_kpis.csv` | `decision_trace.json` |
|---|---|---|
| 无 sidecar（历史断点）| `AF7DD1BAE85631E6` | `8C9AAC97D51DF3F9`（= 基准 ⇒ 零行为变化 ✓）|
| 人为造 sidecar（`bat_weight=7 / cost_weight=3`）| **`AF7DD1BAE85631E6`（逐字节相同 ✓✓）** | `237402093C1DA318`（推演记录的口径变了 ✓）|

⇒ 再次印证：**奖励权重不影响 KPI** ✓（评估不学习、策略固定、奖励也不参与仿真动力学）；
   它只决定"推演里的 reward 属于哪套口径" ⇒ 因此必须**读回训练口径** ✓。

**注意**：现有历史 checkpoint **都没有** sidecar ✗ ⇒ 该机制要真正生效，需用新版训练脚本
跑一次训练（sidecar 随之写入 ✓）。

# §16 eval 出两份文件：详注版 + 精简注释版（2026-10-05）

**决定**：`_gen_marl_split.py` 现在一次生成**三份产物**：`Multi-agent-train.py`（不变 ✓）、
`Multi-agent-eval.detailed.py`（**详注版** ✓）、`Multi-agent-eval.py`（**精简注释版** ✓）。

**为什么**：`Multi-agent-eval.py` 是**平台（Java）与端到端冒烟实际运行**的那份 ✓ ⇒ 它同时
扮演"交付 / 运行"角色，注释越少越便于评审一眼看清流程 ✓；而"每一步为什么这么写"（坑 /
实测数字 / 历史）需要一个**完整保留**的载体 ⇒ 同一份代码、两个注释放大率，分开存放 ✓。

**关键约束（踩过才写下来的 ✗）**：
- **必须一次生成两份** ✗：若做成"先生成详注版、再跑一次 stripper"，一旦漏跑第二步，
  平台运行的就是**旧代码** ✗✗（静默过期，最难发现）⇒ 删详注放在生成器内部完成 ✓。
- **删详注逻辑只有一份实现** ✓：生成器 `from _strip_detail_notes import ast_digest,
  find_blocks, guard_only_comments` 复用它 ✓；为此把该模块的 `sys.stdout` 重绑从**模块级**
  移进 `main()` ✓（否则生成器一 import 就把 stdout 包两层 ✗）。
- **守卫照旧** ✓：块内只允许注释 / 空行（结构上不可能删到代码 ✓）+ 删完 **AST 必须逐字相同**
  ✓，否则 `SystemExit` 且**不写半成品** ✗。
- 生成器自身也要 UTF-8 stdout ✗：末尾打印含 `✓ / ←`，Windows 控制台默认 GBK 会
  `UnicodeEncodeError`（实测崩过一次 ✓）⇒ `main()` 里加守卫 ✓。

**实测（同一 checkpoint / 数据集）**：

| 文件 | 行数 | 详注块 | AST |
|---|---|---|---|
| `Multi-agent-eval.py`（简版 ✓ 平台跑它） | 1057 → **881** | 25 → **0** | `430cc43c52da4038` **不变** ✓✓ |
| `Multi-agent-eval.detailed.py`（详注版） | **1199** | **26/26** | 与简版**逐字相同** ✓ |

- 端到端跑**简版**：`exported_kpis.csv` = `AF7DD1BAE85631E6` ✓、`decision_trace.json` =
  `8C9AAC97D51DF3F9` ✓ ⇒ **逐字节不变** ✓✓（纯注释差异 ⇒ 行为零变化 ✓）。
- 配套改动 ✓：`_q_dup_check.py` 的 `SKIP_FILES` 加入详注版 ✓（否则双胞胎被当"重复实现"报 ✗）；
  `_strip_detail_notes.py` 的 `DEFAULT_FILES` 去掉 eval ✓（它天生已是简版 ✓）；
  `_simple_notes/Multi-agent-eval.py` 删除 ✓（已冗余 ✓）；`MAINTENANCE.md` 的命令清单与
  "不要手改"清单同步 ✓。

# §17 移除 `--trace-every`：落盘间隔固定为 144（2026-10-05）

**决定**：从 `Multi-agent.py` 参数表**删掉** `--trace-every` ✗；三个入口（源 / train / eval）
一律用常量 `DECISION_TRACE_EVERY = 144`（`utils/train_config.py` ✓）。

**为什么（这不是"少一个旋钮"，而是少一份负债 ✓）**：
- 它**几乎从不被调** ✓：144 是经验值（144 步 = 6 天；整回合 ≈ 15 次落盘 ✓），
  扫参时也没人动它 ✗ ⇒ 放在参数表里只会让人以为"这是该调的"✗。
- 它让**三入口共享段**背了一整套兜底 ✗：`getattr(args,'trace_every',144) or 144` →
  `int(...)` → `max(1,…)`。那套写法本身没错（当年正是为挡"train 入口没有这个参数" ✗），
  但**参数一消失，坑就结构性消失** ✓ ⇒ 兜底一起删掉，退化成一个直取常量 ✓。

**连带处理（不清干净会"生成失败" ✗✗）**：
- 生成器里"替 train 裁掉 `--trace-every`"的那一步（`_drop(train, MARK_TRACE_EVERY_ARG, …)`）
  **必须同时删除** ✗ —— 参数没了它会"找不到标记"⇒ 生成器直接报错 ✓；常量 `MARK_TRACE_EVERY_ARG`
  也一并删除 ✓。
- 三份文档串（源 / `EVAL_DOC_BODY` / `TRAIN_DOC_BODY`）的参数说明同步 ✓；
  `utils/decision_trace.py` 与 `utils/train_config.py` 的注释同步 ✓。

**保留什么 ✓**：`--no-trace` **保留** ✓（那是"要不要采集"的开关，与"多久落一次盘"是两件事 ✓）；
`DECISION_TRACE_EVERY` 常量**保留** ✓（它现在是唯一的频率入口 ⇒ 想改就改它，一处生效 ✓）。

**实测**：默认行为**逐字节不变** ✓✓ —— 端到端 `exported_kpis.csv` = `AF7DD1BAE85631E6` ✓、
`decision_trace.json` = `8C9AAC97D51DF3F9` ✓（= 改前基准 ✓）。

# §18 CHESCA 是纯评估算法（无策略训练）—— 但它的预测器**不是**零先验（2026-10-08）

**结论** ✓：`CHESCA.py`（纯 CHESCA 入口）**没有训练过程** —— 一次运行即出 KPI。
它的决策 = **规则 + 在线规划**，不是"学"出来的：

- 主入口是 `checa/agent.py` 的 `predict()`（每仿真小时调用一次）；
- 电池动作来自**树搜索**：`checa/battery_control_search/battery_controller.py` 的 `fit()` 是
  "建搜索树"（向前看 `tau` 步），不是机器学习里的 `fit`；
- 温度 / 热水走设定点与限值规则（`min_soc_per_hour`、`B_low` / `B_high`、`balance_type`）；
- **控制路径**里没有 `optimizer` / `backward()` / `.learn()`；`CHESCA.py` 的 CLI 也**没有任何
  训练参数**（原有 12 个 + 2026-10-08 新增的 56 个配置项，全是配置 / 评估类）。

**⚠️ 三处"看着像训练"的东西（写论文 / 对比表时必须交代）**：

1. **预训练 XGBoost 预测器**：`CHESCA-copy/checa/forecast_agent/pretrained/` 里有 **103 个**
   `xgboost_*.json`（60–170 KB / 个），由 `pretrained_xgboost.py` 在初始化时 `load_model()` 读入。
   ⇒ 所以"CHESCA 无需任何训练"**不严谨**：它无需**策略**训练，但**依赖离线训出的预测模型**。
2. **在线 XGBoost + 集成权重在线更新**（"跑的过程中在学"）：`forecasting_agent.py` 的预测是
   **三路集成**（`use_pretrained` / `use_xgboost` / `use_historical` 全为 True），初始权重
   `[1.0, 0.0, 0.0]`，按误差在线调整（`weight_rate = 0.05`）；在线那路按
   `fitting_frequency = 1`（天）**每天重新 fit 一次**。
   ⇒ 学的是**预测**（负荷 / 光伏 / 温度 / 需求），**不是控制策略**；
   ⇒ 也说明它**不是静态查表**，跑得越久预测越准。
3. **SAC 残差**（真正的训练产物，但只在 ResMARL 模式下出现）：`checa/residual/policy.py` 是
   `nn.Module`（`torch.save` / `load_state_dict`）——CHESCA 侧**只加载推理**
   （`model.eval()` + `corrector.predict_delta()`）；训练在 **MARL 侧**
   （`Multi-agent-train.py` / `train_chesca_resmarl.py` → `multi_agent_checkpoint`），
   且只有 `--marl-mode multi_agent` 才启用（否则 `apply_resmarl_cli_overrides` 强制关闭）。

**对实验与论文的含义**：

- **对比维度**：CHESCA 那列写"**策略训练成本 = 0**"，并单独标注"**含离线预训练预测器 +
  运行中在线自适应**"；MARL 那列才是"训练轮数 / 收敛曲线 / checkpoint"。
  **不要把"收敛曲线"当成两者共同指标**（CHESCA 没有训练阶段）。
- **运行时开销**：CHESCA 不是零成本 —— 每步都要**树搜索 + 预测**（`tau` 越大越贵）。
- **可复现性**：预测器在线 refit ⇒ 跨机器 / 跨时长可能有微差；但**固定配置下实测可复现**
  （2026-10-08：48 步跑两次，`exported_kpis.csv` sha256 均为 `a9e7b2bb3fe39b67`）。
- **`CHESCA-ResMARL`** 是"**有训练的 CHESCA 变体**"，引用时必须标出训练来源
  （`multi_agent_checkpoint`）。

**相关**：2026-10-08 已把 CHESCA 的配置入口改成与 Multi-agent 同一套（代码编辑器「配置」弹窗 →
Java 翻成 `--参数名 值`；优先级 = 命令行 > 配置 JSON > 内置默认）⇒ 见 `MAINTENANCE.md` A53。
