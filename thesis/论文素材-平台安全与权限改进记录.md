## 1. 数据库瘦身：18 表 → 10 表

### 问题
平台早期按 CSV 快照入库，建了 `building_1/2/3`、`pricing`、`weather`、`carbon_intensity` 等表；
后来数据链路改为「直接读 CityLearn schema 的 CSV」，这些表不再参与任何计算，但代码里仍有实体与 Mapper 注入，
造成「看起来在用、实际零调用」的假依赖。

### 做法（可作为方法论写）
1. **判定死表不能只看有没有实体类**，要沿调用链走到终点：
   `BaseDataService.getList()` → `CityLearnLocalDatasetService.getBuildingRows()` → 该方法从 schema 的 **CSV**
   读取碳强度/电价/气象列，Python 侧同样只读 CSV。7 张表因此在链路上完全不被触碰。
2. **判定孤儿表要看有没有展示出口**：`community_building` 唯一页面 `BuildingManagement.vue` 未进菜单、
   `permission` 表里也没有对应菜单码 ⇒ 20 行数据无论如何都显示不出来。
3. **删表流程固定为四步**：`mysqldump` 备份 → 临时库导入恢复 → `CHECKSUM TABLE` + `SHOW CREATE TABLE`
   逐字节比对 → 通过后才 `DROP`；随后把建表语句在 `citylearn.sql` 里整段注释，空库导入验证表数正好。

### 证据
- 备份：`citylearnjava/legacy_tables_20261019.sql`（469,066 B，7 表结构+数据）、
  `citylearnjava/legacy_community_building_20261019.sql`（4,911 B，1 条 INSERT / 20 行）。
- 恢复校验：7 表行数（720×6 + 0）与 `SHOW CREATE TABLE` 逐项一致；
  `community_building` 的 `CHECKSUM TABLE` = 3343971136、行数 20、建表语句与源库逐字节相同。
- 最终库表数：**10**（`information_schema` 实测）；`citylearn.sql` 空库导入 0 错误、正好 10 张表。
- 删除后后端仍返回 `http_code=200`，说明没有隐藏依赖。

### 论文落点
`chap4 §4.4 数据库表结构设计与文件混合存储`：可写「最终 10 张表」的表清单与职责，
并把「CSV 为主的混合存储」作为设计决策说明（数据库只存元数据与结果索引，时序数据留在 CSV/JSON）。

## 2. 操作级权限模型（自建轻量 RBAC）

### 问题
原先权限只有「菜单可见性」：`codeEditor:operate`（保存/运行/改名/新建全包）与 `codeEditor:delete`
两条粗粒度开关。结果是「想让某人能看代码但不能改」无法表达。

### 做法
权限码分两层：

| 层 | 形态 | 例子 | 用途 |
|---|---|---|---|
| 菜单层 | `menu:*` | `menu:codeEditor` | 决定左侧菜单是否出现、对应读接口是否可调 |
| 操作层 | `域:动作` | `codeEditor:run`、`taskList:delete` | 决定按钮是否可点、写接口是否可调 |

- 代码编辑器：2 条 → **6 条**（`save`/`run`/`deleteRecord`/`renameRecord`/`showRecord`/`deleteFile`）。
  拆出 `deleteFile` 的原因：原 `codeEditor:delete` 同时管「删脚本」与「删记录」，拆开后若只给记录一项归属，
  删除脚本就没有权限可分配。
- 任务管理：新增 `create`/`edit`/`delete`/`run` 4 条。
- 参数配置：拆成「单独配置」与「配置组」两棵树，共 10 条
  （`item` + `itemCreate|itemEdit|itemDelete`；`set` + `setCreate|setEdit|setDelete|setMoveIn|setMoveOut`）。
- **旧权限不删只停用**（`enabled=0`）：保留历史行便于追溯，同时不再出现在授权树、不可被分配；
  迁移脚本对存量授权做回填（有 `operate` 的补 `save`+`run`，有 `delete` 的补 `deleteFile`+`deleteRecord`）。
- 后端 `normalizePermissions` 做**父链补齐**：勾了子节点而未勾祖先时，逐级向上补（最多 10 层防环），
  避免「有操作权限但菜单不显示」的自相矛盾状态。

### 证据
- `permission` 表 **30 行 / 26 条启用**（实测），全部权限码在 `PermissionCodes.java`、`permissions.js`、
  `citylearn_data.sql` 三处同步。
- 迁移脚本幂等：重跑后行数稳定在 30，`user_permission` 悬空引用 0 条。
- 空库导入 `citylearn.sql + citylearn_data.sql` 零错误，`menu:codeEditor` 下正好 6 个子节点。

### 论文落点
`chap4 §4.4`（权限表设计）+ 可新增小节「访问控制设计」：说明「菜单级 + 操作级」双层模型
与「父链自动补齐」这一致性约束（后者是可直接写进设计章的一个小贡献点）。

## 3. 接口级鉴权（注解 + 拦截器 + 会话）

### 问题
前端隐藏按钮不等于安全：绕过页面直接 POST 仍能改数据。改造前后端只有登录拦截，没有任何接口级权限判断。

### 做法（三层）
1. `@RequirePerm(...)` 标在 Controller 方法上，多个权限码是 **OR**（任一满足即放行）。
2. `PermissionInterceptor`（order=2，排在 `LoginInterceptor` order=1 之后）：
   无注解直接放行；`SUPER_ADMIN` **不看权限集合直接直通**（即使权限表被改坏也不会把管理员锁死）；
   普通用户要求会话权限集命中至少一个码，否则返回 `code=403`。
3. 登录时把权限码集合写入 `session[LOGIN_PERMS]`；`/web/auth/current`（进页面/刷新都会调）**也重写该集合**
   ⇒ 管理员改完权限，对方刷新页面即生效，不必重新登录。

### 覆盖口径
| 类别 | 数量 | 挂什么权限 |
|---|---|---|
| 菜单级接口（读 + 已读标记） | 34 | `menu:home` / `menu:recDashboard` / `menu:dataList` / `menu:codeEditor` / `menu:taskList` / `menu:algorithmParam` / `menu:resMarlConfig` |
| 写接口 | 22 | 操作码（`codeEditor:save`、`taskList:run` 等） |
| 仅判登录 | 12 | auth 3 + user 8（Service 层 `requireSuperAdmin`）+ file 1（图片流） |

**关键做法（值得写进论文）**：映射必须按「**页面实际调用了什么**」定，不能按接口名字面猜。
共享接口用 OR 数组，例如 `getDatasetList` = {dataList, codeEditor, resMarlConfig}、
`getDashboardSimulationDetail` = {home, recDashboard}、`getPyFileList` = {codeEditor, taskList}。
漏挂一个页面的码，该页必然 403/白屏。

### 证据
- 验证程序 `citylearnjava/target/verify/_verify_perm.ps1` 是**数据驱动全量扫描**：
  遍历 Controller 每个方法，对每个受保护接口断言 4~6 件事（持首个权限放行 / 无关权限 403 且码值正确 /
  超管直通 / 未登录 401）⇒ **56 个受保护接口、0 个无注解接口、353 条断言全过**。
- 对照表 `citylearnjava/接口权限对照表.md` 由 `_gen_api_perm_doc.py` 从源码生成（不手改），
  含「完全没被拦截的接口」章节。

### 已知缺口（论文里不能忽略）
`com.citylearn.demos.web` 下 6 个初始化脚手架接口（`/hello`、`/user`、`/save_user`、`/html`、
`/user/{userId}/roles/{roleId}`、`/javabeat/{regexp1}`）**路径不带 `/web` 前缀，两道拦截器都拦不到**，
且无任何调用方。⇒ 要么删掉整个 `demos` 包，要么论文里只能写「业务接口全部受控」。

## 4. 密码存储：明文 → bcrypt 加盐哈希

### 问题
`user.password` 原来直接存明文（两个账号都是 `000000`），登录用 `password.equals()` 明文比对。
只要有人导出备份或把库传给同学调试，账号即等同公开。补充事实：`UserVO` 里本来就没有 password 字段，
所以用户列表接口并不会把密码回传给前端——泄露面在数据库与代码，不在响应体。

### 为什么是 bcrypt（选型理由，可直接写）
密码**不能"编码"或"加密"**：Base64/十六进制是可逆表示，AES 需要保管密钥且可解，MD5/SHA 是"快"哈希
（一张消费级显卡每秒可算上亿次，`000000` 这种弱口令瞬间破）。正确做法是**加盐慢哈希**。

| 方案 | 内存硬 | 典型参数 | 输出长度 | 本项目可用性 |
|---|---|---|---|---|
| Argon2id | 强 | m=19MiB, t=2, p=1 | ~97 字符 | 需 BouncyCastle，OWASP 首选 |
| scrypt | 强 | N=2^17, r=8, p=1 | ~90 字符 | Spring 自带，内存吃得多 |
| **bcrypt** | 部分 | **cost=10** | **60 字符** | **本项目采用** |
| PBKDF2-HMAC-SHA256 | 无 | 迭代 600,000 | ~80 字符 | JDK 自带，抗 GPU 最弱 |

选 bcrypt 的工程理由：`spring-security-crypto` 一个 jar 即含实现（盐、迭代、恒定时间比较全内置，
不会自己写错），输出 60 字符对现有 `varchar(128)` 字段零改动，生态认知度最高。

### 做法
- 存储格式 **`{bcrypt}$2a$10$<22位盐><31位摘要>`，总长 68 字符**。前缀 `{bcrypt}` 是自加的，
  用来区分「已哈希」与「历史明文」（旧数据是裸串）。
- 封装 `common/PasswordHasher`：`encode()` / `isHashed()` / `matches()`。
  `matches()` 对裸串退化为**恒定时间明文比较**（`MessageDigest.isEqual`），让老账号仍能登录；
  哈希串被手工改坏时返回 false 而不是抛异常（避免登录接口 500）。
- **登录时自动升级**：校验通过后若 `isHashed()` 为 false，立即用新算法写回。
  于是不用停机、不用让任何人改密码，账号在"下一次登录"时各自完成迁移；写库失败不影响登录。
- 新建管理员、重置密码两处入口统一走 `encode()`；明文不落库、不写日志。
- 顺带把 `/web/user/edit` 的密码参数**彻底移除**（只改用户名/显示名称），改密码只剩 `resetPassword` 一条路径。

### 证据
- 单元级（`target/verify/_HashGen.java`）：**13 条断言全过** —— 同密码两次编码因盐不同而不同、
  长度 68 ≤ 128、前缀正确、正确口令通过、错误/空/null 口令拒绝、**历史明文仍可通过**、
  坏哈希串返回 false 不抛异常、单次校验耗时 **55 ms**（证明是"故意慢"的哈希而非快哈希）。
- 端到端（`_VerifyStored.java` 读**数据库里真实存的串**）：2 个账号「000000 通过 / 000000_wrong 拒绝 / 已哈希=true / 长度=68」。
- 活库迁移：`migration_20261020_password_bcrypt.sql`，带 `AND password = '000000'` 条件 ⇒ 幂等，
  重跑不会把用户改过的口令覆盖回默认值。迁移前备份 `user_table_backup_20261020.sql`。
- 种子同步：`citylearn_data.sql`、`src/main/resources/db/user.sql`、`release/` 两侧副本全部改为哈希；
  空库导入后两行 `len=68`，再跑 `_VerifyStored` 仍全过。
- **规则修正**：`db/user.sql` 原来 `ON DUPLICATE KEY UPDATE password = VALUES(password)`，
  重跑脚本会把用户改过的密码重置回 `000000` —— 已删掉这一行；实测「先改成 `CHANGED_BY_USER` 再重跑脚本」后值不变。

### 论文落点
`chap4 §4.4`（用户表字段与安全设计）。措辞建议见第 7 节。

## 5. 决策同步回放（L1.1，可视化增量）

### 做法
在「模型优选 / 决策推演」页签顶部加 `单线回放 | 同步对比` 切换。对比模式渲染新组件
`DecisionTraceCompare.vue`：双 run 互斥选择、并集 step 滑块、播放（1×/2×/4×）、
全段净负荷趋势条 + 游标、左右逐栋动作表、底部「右−左」逐维差值分级着色、封面差异红条警示。
逻辑抽在 `utils/decisionTraceCompare.js`（`alignFrames` / `frameCoverage` / `diffFrames` / `diffLevel` 等），
`ChescaTracePanel` 原单线视图零改动（`traceViewMode` 默认 single）。

### 三个真实数据坑（这是本节最有价值的部分，纯读代码发现不了）
1. **CHESCA 的剧本里没有 `net=`**：社区净负荷只出现在 `[安全审查] 净负荷：4.549 kWh` 行内（逐栋求和）。
   ⇒ 三级兜底解析：`[观测动作] net=`（Multi-agent）→ `[安全审查] 净负荷：`（CHESCA）→
   `[社区负荷] 上步净用电合计`（滞后，最后兜底）。实测 CHESCA **719 步 / 719 步解析成功**。
2. **两侧 step 起点与步数可能完全不同**：CHESCA local 为 `0..718`（719 步），district online 为 `1..2207`（2207 步）。
   ⇒ 对齐按 **step 数值**而非数组下标；覆盖率差 >10% 时界面出红条，提示「很可能来自不同数据集，不可比 KPI」。
   这等于把「local720/online2208 禁比跨 schema 累计」这条研究纪律**做成了前端护栏**。
3. `district.peak_target_kw` / `peak_ratio` **实际落盘为 null**（只有 `ratio_vs_segment_peak` 有值）
   ⇒ 界面峰值比回退为「占全段峰值 %」，而不是假装有目标值。

### 验证
8 项逻辑断言（对齐/覆盖率/乱序去重/diff/缺步/4 维分级）全过；真实 trace 三线抽样通过；
`eslint` 干净、`npm run build` exit=0。**未做浏览器实跑**（需同时起 Spring Boot + MySQL + dev server），
只到编译级验证——论文写「已实现并通过编译与逻辑单测」是准确的，写「已通过端到端 UI 测试」就不准确。

### 论文落点
`chap4 §4.6 前端系统功能实现`（可配一张对比界面截图）、`chap5 §5.1`（作为功能测试用例之一）。

| 编辑管理员不再改密码 | 两个入口（编辑、重置）都能改密码，规则易分叉 | 编辑弹窗只留「用户名 / 显示名称」；后端 `edit` 接口删除 password 参数，即使构造 POST 也会被忽略；超级管理员仍被拒绝编辑 |

## 7. 论文措辞边界（重要，避免被评审抓）

| 不能写 | 应写 | 原因 |
|---|---|---|
| 「密码经过加密存储」 | 「密码经 **bcrypt 加盐哈希**存储，不可逆」 | 加密可解，哈希不可解；术语错会被直接质疑 |
| 「实现了标准 RBAC」 | 「实现了一套**自建的轻量 RBAC**：菜单权限 + 操作码双层」 | 没有引入 Spring Security 全套权限模型，只有 bcrypt 算法借用其 crypto 模块 |
| 「所有接口均已鉴权」 | 「**56 个业务接口**全部纳入鉴权；另有 6 个脚手架示例接口未受控，已计划移除」 | `demos.web` 那 6 个确实拦不到，写"全部"就是假话 |
| 「可防御暴力破解」 | 「通过慢哈希提高了**离线爆破**成本（单次校验 55 ms）」 | 没做登录失败计数/锁定，防不了在线爆破 |
| 「密码可找回」 | 「密码不可逆，遗忘只能由超管**重置**」 | 哈希没有反函数，这也是设计意图 |
| 「端到端测试通过」 | 「编译级验证 + 逻辑单测通过，UI 未做浏览器实跑」 | 多数改动只到编译与断言层（无浏览器自动化） |

## 8. 复现与验收命令

```bash
# 后端编译（离线，用 .m2 里去重后的 jar）
```
